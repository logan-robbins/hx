## Context and store retention

Engineer both prompt context and stored task state for one current application and one active goal. Every record has a retention state: `context` for the next pass, `store` for bounded same-goal continuity, `compress` for a short receipt that replaces detail, or `drop` when it no longer supports an active constraint, pending decision, prerequisite, next action, or current proof.

On compaction, carry forward the current objective, active constraints, map slice, source/config revision, unresolved decisions, required receipts, and the immediate next action. Compress completed work to the smallest receipt that preserves its output identity, input/source revision, check evidence, and remaining uncertainty. Delete obsolete history and prior application states so they cannot be mistaken for current facts. Apply bounded garbage collection at completion, replacement of a prerequisite, source/config revision, and handoff.

A new independent assignment starts clean: load the current source, map, configuration, scoped task packet, and explicit prerequisite outputs. It does not inherit worker memory, another assignment's conclusions, or historical routes. Same-goal continuations may use only validated records scoped to that goal and current application state. Operator-authored policy remains durable configuration; generated observations, summaries, and role-specific records have no lifetime beyond their active-goal need or current proof obligation.

## QA and release retention

QA needs a semantic map of required behaviors, invariants, affected interfaces, failure modes, and coverage claims. Its companion stores independent expected/actual results, reproducible commands, input/seed, environment/source version, and unresolved failures only through the active goal or proof window, then compresses or drops them by the retention rules. QA verifies the behavior against the goal; developer summaries and map descriptions are claims to test. Keep test/fixture edits in assigned scope and route production defects to implementation tasks.

Release needs build/deployment dependencies, artifact identities, compatibility constraints, and rollback contracts. Its companion stores ordered operations and the next action that has not run only until completion or the current proof obligation. Distinguish `planned`, `started`, `confirmed`, and `unknown` operations. Unknown outcomes require reconciliation rather than repetition. Store authorization references and credential locations only for the authorized active operation, never credential values.

Both roles get map slices and continuity support. Deterministic check/build results update the current-goal ledger without a model call; companion extraction handles new findings, decisions, and ambiguous outcomes. Apply the same retention states and garbage collection to those records. Enable it by information need, not job title.

Assign log watching, event offsets, usage accounting, lifecycle control, and wake scheduling to the deterministic observer/controller. Companion prompts receive immutable event deltas and relevant record versions; they must not poll session logs or infer safe reset boundaries. Capture active-goal user corrections and assistant-only conclusions from native messages, with explicit progress for conclusions otherwise unobservable, then compress or drop them when their retention condition ends. Treat reported success as a claim until supported by a receipt.

Use the [compact continuation language](/Users/loganrobbins/workspace/hx/docs/continuity-language.md) for new facts: concise complete propositions, concrete verbs, and explicit conditions/causes/scope. The examples are non-exhaustive. Preserve requirements verbatim and distinguish observed, required, hypothetical, unknown, and unrun states. Remove repeated narration, not semantic qualifiers; do not force every fact into command or status templates.
