# Publishing hx: the productization plan

This is a plan, not a procedure that has been run. **No remote and no GitHub repository have
been created.** Nothing in this document has been executed, and nothing in hx creates a remote
or pushes to one. Executing it is a deliberate, later decision by the spec author.

## 1. The repository

**Name:** `hx`, under the `autodev-team` organization — `github.com/autodev-team/hx`.

The package name on PyPI is `hx`. If that name is taken by the time we publish, the fallback
is `hx-harness` as the distribution name with the import package, the CLI, and the repository
all staying `hx`; only `pyproject.toml`'s `[project] name` and the install command change.

**Public**, MIT-licensed, from the first commit that is published. There is no private-then-open
transition planned; see §6 for what does not go in it.

**Default branch:** `main`. Direct pushes disabled; changes land by pull request with CI green.
Tags are the release mechanism.

### Layout as published

```
hx/
  README.md                  what it is, the three problems, how work flows
  LICENSE                    MIT, autodev-team
  CHANGELOG.md               Keep a Changelog; the public surface is defined at the top
  CONTRACTS.md               JSON shapes shared between the CLI and the UI
  pyproject.toml             name, version, entry points, package data
  src/hx/                    the package: CLI, hooks, companion, adapters, ui, skeleton, skills
  tests/                     unit, guard, ui, packaging
  docs/                      deploy.md, two-worlds.md, github-plan.md
  packaging/                 launchd plists, systemd units, tested-claude-versions.json
  spec/                      the numbered section files, compile.sh, HARNESS_SPEC.md
  .github/workflows/ci.yml   this plan's CI
```

The `spec/` directory ships. It is the design record, it is what the acceptance tests are
written against, and a reader who wants to know why a mechanism exists should not have to ask.
`spec/HARNESS_SPEC.md` is generated by `spec/compile.sh` from the numbered files; the numbered
files are authoritative and CI should eventually assert the compiled file is current.

`ORCHESTRATION.md`, `goals/`, `handoff/`, `tools/`, and `.baseline/` are build-process
artifacts of how hx was written, not part of the product. They are excluded from the published
repository (§6).

## 2. Releasing

hx is a pure-Python, stdlib-only package. The wheel is universal: no compiled extensions, no
platform wheels, no matrix.

```bash
uv build                                   # dist/hx-<version>-py3-none-any.whl + .tar.gz
uv publish                                 # to PyPI, from a trusted-publisher CI job
```

Users install with:

```bash
uv tool install hx
# or
pipx install hx
```

`uv tool install` is the documented path because hx is an application, not a library: it should
live in its own isolated environment with `hx` and `hx-hook` on `PATH`, and those two absolute
paths are what get baked into every agent home's `settings.json` and into the launchd and
systemd units.

### Release steps

1. Land the work. CI green on both runners.
2. Move the `## [Unreleased]` entries in `CHANGELOG.md` into a new `## [x.y.z] - YYYY-MM-DD`
   section. Any change to the `hx` command set, the instance layout, or `CONTRACTS.md` gets a
   **Changed** entry saying what an existing instance must do.
3. Bump `[project] version` in `pyproject.toml`.
4. Confirm `packaging/tested-claude-versions.json` lists every Claude Code version the M6 live
   suite has passed on, newest first (§4).
5. Tag `vX.Y.Z` and push the tag. A `release.yml` workflow — to be added alongside the tag
   protection, it does not exist yet — runs `uv build`, re-runs the wheel content check from
   `ci.yml`, publishes to PyPI via a PyPI Trusted Publisher (OIDC, no long-lived token in the
   repo), and attaches the artifacts to a GitHub Release whose body is the changelog section.

### Versioning

Semantic versioning. Below 1.0.0 the public surface is the `hx` command set (spec 08), the
instance layout (spec 03), and `CONTRACTS.md`; a breaking change to any of them is a minor
bump with a migration note. 1.0.0 waits on M10 passing on a clean macOS and a clean Linux user.

Upgrading the package never writes into a user's instance. `hx upgrade` is the only path that
does, and it is a separate, explicit command (spec 17.6).

## 3. What CI does

`.github/workflows/ci.yml`, on every push to `main`, every pull request, and on demand.

**Job `test`** — matrix `ubuntu-latest` and `macos-latest`, `fail-fast: false`:

1. Install `tmux` (apt on Linux, brew on macOS). hx drives real tmux sessions; a runner without
   tmux would pass a suite that proves nothing.
2. `actions/setup-python` at 3.14, then build `.venv` with `pytest` and `pip install -e .`, so
   CI runs through the same `.venv/bin/python` the lanes use locally and
   `tools/milestone-check.sh` needs.
3. **Record a guard baseline from a fresh Claude home.** `tests/guard/test_user_home_untouched.py`
   compares `~/.claude` against a manifest recorded before the build began. A runner has no
   such history, so the job creates an empty `$RUNNER_TEMP/guard-home/.claude`, hashes it with
   `tools/claude-home-hash.sh` into `$RUNNER_TEMP/guard-baseline/claude-home.manifest`, and
   points the test at both through `HX_USER_CLAUDE_HOME` and `HX_CLAUDE_HOME_BASELINE` (the two
   environment variables the test already honours). The assertion is the real one: nothing in
   the suite wrote to the Claude home it was given. `.baseline/` is gitignored precisely so a
   developer's local manifest is never what CI checks against.
4. Run `tests/guard` on its own first, so a guard failure is never buried in suite output.
5. Run `tools/milestone-check.sh` — the same script every lane runs before finishing a goal.

**Job `package`** — `ubuntu-latest`:

1. `uv build`.
2. Assert the wheel actually contains its data files: `hx/skeleton/templates/work-item.md`,
   `hx/skeleton/companion/BASE.md`, `hx/skeleton/config/CLAUDE.md`, `hx/skeleton/PARTNER.md`,
   and both `SKILL.md` files. `pyproject.toml` declares them as package data; if that
   declaration silently stops matching, `hx install` ships with nothing to copy and no other
   test in the suite notices.
3. `uv tool install --from dist/*.whl hx` and confirm `hx` and `hx-hook` are on `PATH`.
4. Upload `dist/` as an artifact.

### Not in CI, and why

The M6+ milestones run a live Claude Code against a real account. That needs credentials, costs
money per run, and is non-deterministic in wall-clock terms. It stays a local and pre-release
gate — specifically the gate `hx upgrade` enforces before pinning a new Claude Code version —
and never becomes a pull-request check. CI covers everything that runs against the fake
`claude` and the fixtures.

Branch protection on `main`: both `test` jobs and `package` required, linear history, no force
push.

## 4. Pinning Claude Code

hx runs the same `claude` binary the user already has, but it runs it at a version the suite
has actually passed on.

- `hx install` records `{bin, version}` in `config/claude.json` and refuses to install if that
  version is not in the package's tested list.
- The tested list is `packaging/tested-claude-versions.json`:
  `{"versions": ["2.1.278"]}`. Entries are the bare version number as `claude --version`
  reports it before the ` (Claude Code)` suffix, newest first; the first entry is what a fresh
  install expects. **2.1.278** is the version this plan was written against, and it is there
  because 2.1.274 fixed the one documented gap in `/goal` survival (goal loss on `--resume`
  after compaction) that the seam mechanism depends on.
- Sessions launch with `DISABLE_AUTOUPDATER=1` and the recorded absolute binary path, so an
  upstream release cannot change a running fleet underneath its operator.
- `hx upgrade` is the only way the pin moves: it re-renders every agent home's settings and
  skills from the new package, and if `claude --version` changed, runs the M6 live suite
  against it in a scratch instance **before** writing the new version to `config/claude.json`.
  A failed suite leaves the existing pin in place and says why.

**Adding a version to the list is a human act with evidence behind it.** The pull request that
adds an entry states which live suite run passed on it, on which OS. A version is never added
because it exists.

The list is append-only in practice. Removing an entry breaks `hx install` for anyone holding
that version, so a version known to be broken gets a **Changed** changelog entry and a minor
bump, not a silent deletion.

## 5. Issues, contribution, and support posture

`CONTRIBUTING.md` — to be written before the repository is published — says:

- The spec is the design. A pull request that changes behaviour changes the relevant
  `spec/NN-*.md` section in the same commit and regenerates `spec/HARNESS_SPEC.md`.
- Milestone acceptance tests (spec 13) are the bar for a behavioural change.
- No runtime dependencies are accepted. hx is stdlib-only, on purpose: it is installed as a
  tool on machines that also run an agent fleet, and its dependency surface is part of its
  isolation story.
- Issue templates: a bug template that asks for `hx doctor` and `hx board` output, the OS, the
  `claude --version`, and the relevant part of `hx show <id>` — never a raw transcript, which
  carries the user's own code.

Support posture at launch is best-effort, stated plainly in the README rather than implied by
an issue template promising triage.

## 6. What stays private

Nothing sensitive is in the repository today, and the rules that keep it that way:

- **The build process.** `ORCHESTRATION.md`, `goals/`, `handoff/`, `tools/`, and `.baseline/`
  are how hx was built by a fleet of agents in parallel. They name local paths, tmux session
  names, and lane assignments, and they would read as instructions to anyone who cloned the
  repo. `tools/claude-home-hash.sh` and `tools/milestone-check.sh` are referenced by
  `ci.yml`, so publishing means either moving those two under `.github/scripts/` or shipping
  `tools/` while excluding the rest. Decide at publication; the CI workflow's paths are the
  only thing that changes.
- **Anything derived from the prior product.** `/Users/loganrobbins/workspace/autodev` is
  material that was mined, not vendored. No autodev file is copied into hx, and its `website/`
  was never read. `spec/AUTODEV-COMPARISON.md` discusses it in the abstract and contains no
  autodev source; it can ship or not, and shipping it is the better choice because it explains
  why several mechanisms exist.
- **Credentials, always.** hx never stores a token in the repository. Instance credentials live
  in `$HARNESS_ROOT/seed/home` and `run/<id>/home/`, both outside the package. The UI's bearer
  token is `run/ui-token`, mode 0600, generated per instance. PyPI publishing uses a Trusted
  Publisher, so no token exists in repository secrets either.
- **Instance data.** `config/`, `orders/`, `pods/`, `logs/`, `state/`, `run/`, `archive/`,
  `repos/`, `wt/` belong to a user's `$HARNESS_ROOT` and never to this repository. Only the
  *skeleton* under `src/hx/skeleton/` is shipped, and the only id in it is `partner`: the
  example worker ships as `templates/worker/`, templated on `{{id}}`, and is not installed.
- **Real repository contents of any user.** Agent worktrees are cut from a bare mirror inside
  the instance. Nothing about a user's product repo is ever collected, and the bug template
  asks for board and doctor output rather than transcripts for exactly this reason.
