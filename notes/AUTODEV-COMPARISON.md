# HARNESS_SPEC vs autodev — functional reassessment

Scope: runtime behaviour only. Continuity and compaction, identity and memory, task delivery, keeping the agent working, completion, blocked and decision handling, dependencies, supervisor wake, restart, subagents. Not in scope: UI, git integration, Pillar contracts, schema vocabularies, digest pinning, tests, packaging. autodev's Project Manager and GM chat map to the spec's Partner; autodev's "Orchestrator" (the human's own chat) maps to the human; autodev workers map to HarnessAgents.

## Rejected from autodev, and why

- Prompt or identity text as command-line arguments: replaced by files and a pointer everywhere.
- The eight-step worker loop pasted into every session: the spec's standing instructions live in the work item, read once.
- Ledger events and `task progress --message`: the raw stream and `## Tasks` edits already carry this.
- Contract digest pinning, Pillar contracts, schema vocabulary, publication and git integration, UI, GM chat mailbox, employee-edit receipts: platform features outside runtime behaviour; revisit when the product is rewritten to the spec.

## Where autodev falls short of the spec's thesis

- Nothing keeps a harness working past the end of a turn.
- Context resets are handled by advice, not mechanism; auto-memory leaks across agents.
- No supervisor process and no wake.
- Its own `gtm/` deployment reinvented the spec's work item and handoff memory by hand.

The spec, with this pass's additions, is the design the product rewrite targets.
